### 2.0 Comparison core: compare, revision listing, rendering and the change-item model

**Depends on:** 1.0 (worker, engine wrapper, Node test helper).

**Specs:**
- Compare settings (`src/engine/settings.ts`), exactly:
  `{ preAcceptInputRevisions: true, compareHeadersFooters: false, trackNumberingChanges: false, detectMoves: true }`.
- Engine calls: `docxDiffCompare(original, edited, settings)` → redline bytes; `getRevisions(redline)` → `RevisionListEntry[]`. Do not use `compareDocuments`.
- If either input already contains tracked changes (check `getRevisions(input).length > 0` before comparing), set `CompareResult.inputsHadRevisions` so the UI can tell the user (FR-13).
- The compare pipeline also tags and renders (tagging rules in task 4 specs; rendering moved here because the range index needs the HTML): the worker returns the untagged redline (for export) and the tagged HTML (for display and indexing).
- `ChangeItem`:
  ```ts
  interface ChangeItem {
    id: string;                 // stable: the first engine revision id it contains (ids are deterministic per inputs + engine version)
    kind: 'inserted' | 'deleted' | 'replaced' | 'formatting' | 'moved' | 'paragraph';
    revisionIds: string[];      // all engine revisions this item decides (incl. folded paragraph marks)
    removedText: string;        // '' when none
    addedText: string;          // '' when none
    description?: string;       // formatting: from the HTML title, e.g. "Bold removed, Font changed"
    location: { scope: 'body' | 'footnote' | 'endnote' | 'table'; noteId?: string };
    wordDelta: { removed: number; added: number };
    order: number;              // document order index
    anchors: string[];          // affectedAnchors unids, for scrolling and range
  }
  ```
- Item rules (PRD §7.2 step 3). Formatting revisions are interleaved with content revisions in the engine list, so apply the next three rules to the sequence of **non-formatting** revisions:
  - Paragraph marks: a `paragraph_mark` revision whose `text` is only `¶` characters joins the previous or next content revision in that sequence if they share an affected anchor (prefer previous); otherwise it becomes a `paragraph` item. A `paragraph_mark` revision with other text is an ordinary `deleted`/`inserted` item.
  - Replaced: a `content_delete` and a `content_insert` that are neighbours in that sequence, in **either order**, and share an affected anchor become one `replaced` item. Pair greedily left to right; a revision joins at most one pair.
  - Moves: one `move` revision → one `moved` item (the entry covers both halves).
  - Formatting: every `type: "format"` revision (`rPrChange`, `pPrChange`, `sectPrChange`) → one `formatting` item.
- `DocIndex` (`src/model/docIndex.ts`, main thread, native `DOMParser` on the rendered HTML):
  `{ blocks: { unid, scope: 'body' | 'fn' | 'en', inOriginal: boolean }[], bodyParagraphs: string[] /* unids of Original body paragraphs, in order */, noteRefs: Map<noteId, unid /* body paragraph */> }`.
  Blocks come from elements with `data-anchor` (kind/scope from `data-source-anchor-id`, e.g. `p:body:…`, `p:fn:…`); `inOriginal` = the block is not wholly inside `ins`/`.rev-move-to`; note refs from `a.footnote-ref[data-footnote-id]` (check the endnote equivalent on a fixture).
- Range (`src/model/range.ts`): `detectTrailingRegion(items, index)` returns the index (in `bodyParagraphs`) of the first anchor of the delete-type body item whose anchors include the **last** Original body paragraph, or `null`. Do not require it to be the last item. `classify(items, index, endPoint | null)` returns `inRange` / `outOfRange` per item; note items follow the paragraph that references the note; an item spanning the end point is out of range.
- Expected on the sample pair (verified in the PRD review with these settings): **796** revisions — 378 formatting, 200 content delete, 167 content insert, 49 paragraph mark, 2 moves; 25 of the 49 paragraph marks fold; 110 delete→insert + 143 insert→delete neighbour pairs share an anchor; the tail is one `paragraph_mark` delete (117,771 characters, 579 anchors); 18 tail footnote deletions.
  Measured in 2.6–2.8 (PRD §7.2, §7.5): 43 of the 49 paragraph marks are bare and **26** fold; the 110 + 143 neighbour pairs overlap, and greedy pairing gives 147 Replaced items (29 + 118); **15** footnote deletions are in the tail (18 in all). 623 items.

### 3.0 Export core: reject-rewrite plus one stateless accept pass

**Depends on:** 2.0 (`ooxml.ts`, revision list with `constituentKeys`, `ChangeItem.revisionIds`).

**Specs:**
- `exportDocx(redline: Uint8Array, revisions: RevisionListEntry[], finalDecision: Map<revisionId, 'accept' | 'reject'>): Promise<Uint8Array>`.
- Every revision must have a final decision; a missing one is a programming error (throw).
- Locate markup by `constituentKeys` via `ooxml.ts` (key formats in PRD §7.3; move range markers have no `kind=` prefix, move keys have a `:name=` suffix; `parseConstituentKey` in `ooxml.ts` handles both). Search `document.xml`, `footnotes.xml`, `endnotes.xml` (per the revision's `partUri`).
- Runs in the worker → XML through `@xmldom/xmldom`, not `DOMParser`.
- Reference: `tasks/reference/reject-all-prototype.py` implements these rules for reject-all and produced exactly the Original text, 0 remaining revisions and `verifyDeliverable: passed` on the sample. Port its behaviour, not its structure (it rewrites every revision; ours rewrites only the selected ones).
- Rewrite rules for **reject** (PRD §7.3):
  | Markup | Rewrite |
  |---|---|
  | `w:ins` around runs | rename to `w:del`; `w:t` → `w:delText`; `w:instrText` → `w:delInstrText` |
  | `w:del` around runs | unwrap (keep children); `w:delText` → `w:t`; `w:delInstrText` → `w:instrText` |
  | `w:rPrChange` | replace the parent `w:rPr` children with the `w:rPrChange/w:rPr` children; drop `w:rPrChange` |
  | `w:pPrChange` | replace the `w:pPr` children with: the `w:pPrChange/w:pPr` children **first**, then the existing `w:rPr` (paragraph mark), then the existing `w:sectPr`. Wrong order still gives the right text but fails `verifyDeliverable` (schema) — seen in the prototype |
  | `w:sectPrChange` | replace the `w:sectPr` children with: existing `w:headerReference`/`w:footerReference` first, then the `w:sectPrChange/w:sectPr` children |
  | paragraph mark `w:pPr/w:rPr/w:ins` | rename to `w:del` |
  | paragraph mark `w:pPr/w:rPr/w:del` | remove the element |
  | `w:moveFrom` | unwrap, `w:delText` → `w:t`; remove matching `w:moveFromRangeStart/End` |
  | `w:moveTo` | rename to `w:del`, `w:t` → `w:delText`; remove matching `w:moveToRangeStart/End` |
  | `w:trPr/w:ins` | rename to `w:del` (the inserted row will be removed) |
  | `w:trPr/w:del` | remove the marker (the deleted row stays); also apply the `w:del`-around-runs rule to the row's content |
  | `w:cellIns` | rename to `w:cellDel` |
  | `w:cellDel` | remove the marker |
  | anything else | throw `UnsupportedRevisionError(revisionId, family)` |
- The table rules are **untested** (the samples have no tables): confirm them with the table fixtures in 3.5, and adjust if the round trip fails.
- After the rewrite: `docxDiffAcceptRevisions(bytes)`, then `getRevisions(result)` must return `[]`; otherwise throw.
- A revision with `resolutionStatus !== 'supported'` → `UnsupportedRevisionError` (FR export error message, task 7).
- Performance target: ≤ 10 s for ~300 pages (FR-44).

### 5.0 Review workflow: changes list, decisions, navigation, overview bars

**Depends on:** 4.0 (panels with `data-change-id`, compare result in app state).

**Specs:**
- Decision state (`src/model/decisions.ts`): `Record<itemId, 'accepted' | 'rejected'>`; absent = undecided. Actions: `set(id, d)`, `reset(id)`, `acceptAllUndecided(filter)`, `rejectAllUndecided(filter)`, where `filter` selects text items, formatting items, or both. Out-of-range items are excluded from every bulk action.
- `finalRevisionDecisions(items, decisions, range, undecidedChoice)` → `Map<revisionId, 'accept' | 'reject'>` for export: out-of-range → reject; decided → its decision; undecided → `undecidedChoice`.
- List order: document order of text items; the formatting group appears as one entry at the position of its first item, collapsed by default (FR-30). Virtualize with `@tanstack/react-virtual`.
- Current change: one `currentItemId` in app state. Selecting an item scrolls both panels so its first element (`[data-change-id]`) is centred; the element gets a "current" outline.
- Navigation order: in-range text items; plus formatting items when the formatting group is expanded (FR-31).
- Shortcuts (proposed, PRD open question 3): `j`/`↓` next, `k`/`↑` previous, `a` accept current, `r` reject current, `u` reset current, `?` help. Ignore shortcuts while focus is in an input. After `a`/`r`, move to the next undecided item.
- Decided styling (FR-25): `[data-change-id]` elements of accepted items get a dimmed highlight + ✓ marker class; rejected get dimmed + ✗. Apply by toggling classes on the existing DOM elements (no re-render of the HTML).
- Overview bar: a vertical strip per panel; for each item, a mark at `elementTop / scrollHeight` coloured by kind (decided items lighter). Recompute on resize. Click → scroll to that position.
