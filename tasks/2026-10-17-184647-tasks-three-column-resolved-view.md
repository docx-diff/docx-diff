### 0.0 Check (and fix) the side panels' paragraph join before a table

**Background** (found while reviewing the plan, 2026-10-17): `mergeJoinedParagraphs`
(`src/ui/renderedDocument.ts`) moves the content of a paragraph whose mark the panel's version
lacks to the start of the next shown `[data-anchor]` sibling. A `table` also has `data-anchor`, and
nothing checks that `next` is a paragraph. So a paragraph whose mark is deleted (right panel) or
inserted (left panel) just before a table could have its text moved **into the `<table>` element**,
before its first row. No fixture covers it, so this is unconfirmed.

**Specs**

- Expected behaviour, matching Word/the export: a paragraph can only join a following **paragraph**.
  When the next shown sibling is a table (or there is none: end of the body, cell or note), the
  export's accept pass drops such a paragraph (`docs/architecture.md`, "Comments": "drops such
  paragraphs when no paragraph with a kept mark follows them before the next table or the end of
  their container"). Confirm what the export actually does with the paragraph's **text** in that
  case (dropped, or kept as its own paragraph) before deciding what the panel shows.
- Whatever the panel shows must agree with the export of the same version (accept-all for the
  right panel, reject-all for the left).
- The fix (if needed) is the guard the Resolved column needs anyway (task 1 specs: "a join never
  crosses a table or the end of its container"), so do it in the shared join, in the form task 1.4
  generalizes.

**Depends on:** `src/ui/renderedDocument.ts`, `test/fixtures/make-fixtures.ts`, `test/fixture-pairs.test.ts`, `test/text.ts`.

**Findings (2026-10-17):** not a real bug in the app. The converter wraps every table in a
`<div align=…>` without `data-anchor`, so `next` was that `div` and the join already stopped there.
The engine puts a mark-removed paragraph right before a table only when the whole paragraph goes
(its text moved into the table's first cell, and the reverse: `paragraph-join-table`); such a block
is `not-in-edited`/`not-in-original` and skipped. The export's accept pass (`docxDiffAcceptRevisions`
on hand-written redlines) **keeps** the text of a mark-removed paragraph before a table, or last in a
cell, as a paragraph of its own; it does not drop it. The guard (`next` must be `p`/`h1`–`h6`) is
defensive; a bare `table[data-anchor]` sibling would have received the text. The task 1 specs below
are corrected accordingly (leave such a paragraph, don't hide it).

### 1.0 Resolution model and DOM logic

**Specs**

- `resolvedItemDecisions(items, state, range, ignored): Map<itemId, 'accept' | 'reject'>`, per item, in this order:
  out of range → `reject`; formatting item (including `change-as-formatting` relabels) → `accept`
  (the column always shows the Edited's formatting, PRD-9; this deliberately ignores
  `formattingChoice`); explicit decision; ignored → `accept`; otherwise (undecided) → `accept`.
  For every non-formatting item this must equal `finalRevisionDecisions(…, 'accept', …)` for its
  revisions: test that.
- DOM state is set by code, as classes, not by CSS attribute selectors, so that jsdom tests can read
  the result: `resolved-hidden` on what the export drops. CSS (`panel.css`) only says
  `.doc[data-side='resolved'] .resolved-hidden { display: none }`.
- HTML shapes (verified on the fixtures during the review; re-check in 1.1 for anything new):
  every `ins`/`del` (incl. `rev-move-from`/`rev-move-to`) has the item's `data-change-id`; a
  paragraph-mark revision has it on the block (`p.rev-para-ins`/`rev-para-del`), and that item can
  differ from the item of the block's text (`paragraph-join`: an "inserted" item owns a
  `rev-para-del` block); `tr.rev-row-ins/del` has the id, its `td`s don't, its paragraphs carry
  paragraph-mark ids of the same item; a note `li` has no id, its paragraphs and the reference
  number (`ins`/`del` around it) do; `span.rev-para-mark-del` (the ¶ glyph) has no id.
- Per element, with `d` = the resolved side of the element's own `data-change-id` (decide by the
  element's tag/class, never by the item's kind):
  - `del` (incl. `del.rev-move-from`) hidden when `d = accept`; `ins` (incl. `ins.rev-move-to`) hidden when `d = reject`.
  - `tr.rev-row-ins` hidden on reject, `tr.rev-row-del` hidden on accept.
  - `span.rev-para-mark-del`: always hidden (a left-panel aid, no id).
  - `.rev-del-marker`, `.rev-move-from-marker` (no fixture produces them): hide like a `del` of the
    closest ancestor with a `data-change-id`, else always.
  - Elements without a `data-change-id` (unchanged text) are never hidden.
- Paragraph marks: a block (`[data-anchor]`) loses its mark when it is `p.rev-para-ins` with `d = reject`
  or `p.rev-para-del` with `d = accept`. A block whose mark is lost continues in the next **sibling
  paragraph** that keeps its mark: same move as `mergeJoinedParagraphs` (content to the start of the
  next kept block, after its list label; the emptied block gets `merged-into-next`). Guards:
  - A join never crosses a table or the end of its container (cell, note `li`, body): `next` must be
    a paragraph-like block (`p`, `h1`–`h6`), not `table[data-anchor]` or the table's wrapper `div`.
    When no kept paragraph follows, leave the paragraph as it is: the export's accept pass keeps its
    text as a paragraph of its own (task 0.0 findings; when its text is gone too, it shows nothing
    anyway). Let the parity tests (1.9, 1.10) confirm; add a unit case.
  - Unlike the side panels, joins must be **undoable**: on a decision change, restore the affected run
    of blocks from their saved child lists, then join again. Save the lists **after** inserting the
    markers (3.1), so markers come back with them. Comment icons (4.2) are not in the saved lists:
    remove them from a run before restoring and re-add them after joining.
  - The side panels' `mergeJoinedParagraphs` got the same boundary check in task 0.0 (`PARAGRAPH_BLOCK`). Build the
    Resolved column's join on that fixed version, and keep the side panels' behaviour as task 0.0
    left it.
- Notes: a note `li` (`li[id^="fn-"]`, `li[id^="en-"]`) is hidden when none of its blocks shows any
  text (all hidden or merged; ignore `.fn-backref`/`.en-backref` "↩" and list labels). Whole-note
  items follow their reference's item (`foldWholeNotes`), so the per-element rules already give the
  right text.
- Out of range: same rules (they resolve to `reject`), plus the `out-of-range` block classes and the
  divider exactly as in the left panel.
- Range order (PRD-6): top-level body blocks with a position (`blockPositions(index, suggestedEndPoint)`)
  **before** the end point that come **after** the first out-of-range block in the DOM are moved, in
  order, to just before it (before the divider). That is the HTML counterpart of `planRangeOrder`
  (which moves each later body element holding an in-range text change). Redo it when the range
  changes: undo the previous moves (remember each moved block's original next sibling) first.
- `resolvedText(wrapper): string[]`, mirroring `docxText` (`test/text.ts`): one line per shown
  paragraph of the body, then of the notes; whitespace-normalised; empty lines dropped. Skip
  `resolved-hidden`, `merged-into-next`, `[data-list-marker]`, `.fn-backref`/`.en-backref`,
  `a.footnote-ref`/`a.endnote-ref` (Word's reference marks have no `w:t`), markers and comment icons.

**Depends on:** `src/model/decisions.ts` (`finalRevisionDecisions`, `reviewableItems`), `src/model/range.ts`

`test/text.ts`, the fixture and sample harnesses (`test/fixture-pairs.test.ts`, `test/sample-pair.test.ts`).

### 2.0 The Resolved column in the layout

**Specs**

- `ViewSettings` gets `threeColumns: boolean`. `DEFAULT_VIEW_SETTINGS = { inlineCard: true, changesList: false, outline: false, threeColumns: true }`.
  Stored settings are merged over the defaults (`load()` already does it), so a browser with stored
  sidebar settings keeps them and only gets the new `threeColumns: true` (PRD-4).
- `useNarrowWindow(): boolean` = `matchMedia('(max-width: 1024px)').matches`, live (listen to `change`);
  `false` without `matchMedia`. Effective view: `threeColumns && !narrow` (PRD-5). The stored setting is
  never changed by the fallback.
- `ColumnsToggle` props: `{ threeColumns: boolean; disabled: boolean; onToggle(): void }`. Label/tooltip
  "Show two columns" / "Show three columns"; when disabled: "The window is too narrow for three
  columns". `aria-pressed={threeColumns}`. Icon shows the target view (two or three vertical bars, e.g.
  inline SVG or `▥`-style glyph matching `ThemeToggle`'s `button--icon`). Placed just before
  `ThemeToggle` in `App.tsx`'s header (PRD-2).
- Panel order Original | Resolved | Edited. The middle panel: `DocumentPanel` with `side='resolved'`,
  title "Resolved" with tooltip "Shows the resolved text; formatting as in the Edited document"
  (PRD-9), `data-testid="panel-resolved"`, no overview bar (PRD-31), never the inline card (PRD-19).
- Scroll sync over N panels: on a scroll of panel *i*, map its position to every other panel with the
  pairs for (*i* → *j*), measured lazily and dropped on resize (as now). Cache `measureBlocks` **per
  panel** (one layout read per panel per invalidation), not per pair: six directions with three panels.
  The middle panel's height changes with most decisions, so its ResizeObserver drops the cache often.
  That is fine (it is re-measured on the next scroll), but don't re-measure eagerly. The effect must
  re-run when the panel list changes (toggle): pass the refs as an array whose identity changes with
  the view, or add the view to `contentKey`. `align(source, target)` unchanged.
- The middle panel is **mounted only** in effective three-column view (the two-column view costs
  nothing). Toggling mounts it fresh: clone, prepare, apply all decisions, then align it with the left
  panel (`align`).
- Clicks (PRD-16): a click in the middle column calls `onChangeClick` → `select(id, false)` like the
  side panels (no scrolling); list/keyboard/Previous/Next selection reveals in all mounted panels.
- Global `.doc` rules in `panel.css` that must not hit the middle panel: the decided `opacity: 0.5`,
  the `::after` ✓/✗ selectors (redone for the resolved side in 3.3). Scope them to
  `.doc:is([data-side='left'], [data-side='right'])` or override in the resolved rules. Rules
  that should apply as-is: `merged-into-next`, `change-current`, the plain-text rule for
  ignored/as-formatting/common/out-of-range, the pointer cursor.
- Padding in three-column view: `.doc` lives in the shadow root, so a class on `.panels` can't reach
  it. Use a custom property (e.g. `--doc-padding-inline`, default `2rem`) that `panels--three` sets on
  the page side and `.doc` reads inside the shadow root (custom properties inherit into shadow roots,
  as the colour tokens already do).
  `revealItem(scrollers[], …)` / `revealBlock(scrollers[], …)`: centre/top every panel that shows the
  element, then align the others with the first panel that showed it (PRD-16, PRD-29, PRD-30).
- The resolved decisions passed to the panel: `useMemo(() => resolvedItemDecisions(items, review, range, ignored))`.
  The panel calls `applyResolution` with only the items whose resolved side changed (keep the previous
  map in a ref, as `appliedDecisions` does).
- Scroll anchoring (PRD-10): before `applyResolution`, remember the first block visible at the top of
  the Resolved panel and its offset; after, scroll so it is at the same offset (`scrollQuietly`, so
  the sync doesn't bounce).

  item has no shown element at all. A shown marker of a decided item shows the ✓/✗ on yellow; of an
  undecided item a small dotted placeholder (PRD-14). Markers are inline and must not add text to
  `resolvedText`. Guards from the review:
  - An item that spans the body and a note (a whole-note deletion: the reference number and the

    lists are saved (task 1 specs).

### 4.0 Comment bubbles in the Resolved column

**Specs**

- Which comments: items with `review.comments[id]?.trim()`, not out of range, not formatting (same
  filter as `exportComments`, without the decision) (PRD-20, PRD-27).
- State in `App.tsx`: `closedBubbles: Set<itemId>`, not stored anywhere (PRD-24). When an item's comment
  is removed or blanked, drop it from the set, so a new comment on it opens (PRD-25). Reset with each
  comparison (`reviewKey`).
- `CommentBubbles` props: `{ comments: { itemId, anchors, text }[]; closed: ReadonlySet<string>; onClose(id); scrollerRef }`.
  Renders one `div.comment-bubble[slot=…]` per open comment, positioned like `InlineChangeCard`
  (`changeBox` + GAP below, clamped to the panel width), text read-only (`white-space: pre-wrap`),
  × button (`aria-label="Hide comment"`) in the top-right corner (PRD-21, PRD-22). Positions recomputed on
  resize of the scroller/content with **one** ResizeObserver + rAF for all bubbles (not one per bubble);
  `changeBox` reads layout per bubble, which is fine for dozens of comments. Also re-place after
  decisions (the text moves even when the size doesn't).
- Like the inline card, bubbles are light-DOM children of the scroller: page CSS applies, and
  locators on `panel-resolved` also match their text. Use `.comment-bubble` / test ids in e2e.
- Stacking (PRD-26): sort open bubbles by top; if a bubble's top is above the previous bubble's bottom +
  4 px **and** they overlap horizontally, push it down.
- Comment icon (PRD-23): `applyResolution`/decision code inserts or removes a
  `span.comment-toggle[data-comment-for=itemId][role=button][tabindex=0]` right after the item's
  `change-decided-end` element / last shown element / shown marker. Its title and `aria-label`:
  "Show comment" / "Hide comment" (`aria-expanded`). The panel's click handler checks
  `closest('.comment-toggle')` first and calls `onToggleComment(itemId)` **without** selecting; Enter/Space
  on it do the same. The icon must not add text to `resolvedText`.
- The slot for bubbles: a second named slot in the panel's shadow root (`comment-bubbles`), next to
  `CARD_SLOT`.
