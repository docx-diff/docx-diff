# PRD: In-browser DOCX Compare, Review and Export

## 1. Introduction / Overview

We need a tool that compares two Word documents (`.docx`) — an **original** and an **edited** version — and lets a reviewer go through every difference, accept or reject each one, and export a new `.docx` with those decisions applied.

The tool runs **entirely in the browser** and is deployed as a static site on **GitHub Pages**. Documents never leave the user's machine.

The UI follows the layout of Draftable's comparison view (reference screenshot, not in the repository): two document panels side by side with changes highlighted, and a list of changes on the right.

The motivating use case is editing translations: an editor revises a long manuscript (e.g. `docs/aramlo-part-2-2025-05-06.docx`, ~60 pages, 746 paragraphs, 20 footnotes) and sometimes delivers only the part revised so far (e.g. `docs/aramlo-part-2-2025-05-06.edited-until-p257.docx`, the first 76 paragraphs). The edited file may also have been restyled (in the sample, the Palatino font and colours were removed throughout). The reviewer needs to see what changed, decide per change, and produce a clean final document.

**Goal:** a reviewer can load two `.docx` files, review all changes in a side-by-side view, accept/reject them individually or in bulk, and download a correct `.docx` reflecting their decisions — with no server involved.

## 2. Goals

1. Compare two `.docx` files in the browser and show word-level differences highlighted in two synchronized panels.
2. Detect text insertions, deletions, replacements, formatting changes and moved paragraphs, in the main body, footnotes/endnotes and tables.
3. Let the user accept or reject each change, all formatting changes at once, or all changes at once.
4. Export a clean `.docx` with all decisions applied, with a user-selectable rule for changes left undecided.
5. Handle a partially edited document correctly: content after the end of the edited region is not reported as a deletion and is preserved in the export.
6. Remember the review in progress in the browser so the user can close the tab and continue later.
7. Work comfortably with documents up to ~300 pages.
8. Deploy as a static site on GitHub Pages; no backend.

## 3. User Stories

- **US-1** As a reviewer, I want to drop an original and an edited `.docx` into the page, so that I can see their differences without installing anything or uploading my files anywhere.
- **US-2** As a reviewer, I want to see the two documents side by side with deleted text highlighted on the left and inserted text highlighted on the right, so that I can read each change in context.
- **US-3** As a reviewer, I want a numbered list of all changes (type, removed text, added text), so that I can work through them systematically.
- **US-4** As a reviewer, I want to click a change in the list and have both panels scroll to it, so that I can see it in context instantly.
- **US-5** As a reviewer, I want previous/next buttons and keyboard shortcuts to step through changes, so that I can review quickly without the mouse.
- **US-6** As a reviewer, I want to accept or reject each change individually, and to accept/reject all, so that I control exactly which edits go into the final document.
- **US-7** As a reviewer, I want moved paragraphs to appear as one "moved" change rather than a deletion plus an unrelated insertion, so that I don't have to reconcile them by hand.
- **US-8** As a reviewer, I want changes inside footnotes and tables to be detected too, so that nothing is missed.
- **US-9** As a reviewer who received a partially edited document, I want the tool to detect where the edited part ends (and to let me adjust that point), so that the unedited remainder isn't shown as hundreds of deletions and is kept in the exported document.
- **US-10** As a reviewer, I want to choose what happens to changes I haven't decided on (accept them or reject them) when exporting, so that the output matches my intent.
- **US-11** As a reviewer, I want my decisions to be remembered if I close the tab, so that I can review a long document over several sittings.
- **US-12** As a reviewer of a restyled document, I want formatting-only changes kept in their own group that I can accept or reject in one step, so that hundreds of font changes don't bury the text edits I actually need to read.

## 4. Functional Requirements

### 4.1 Loading documents

1. The system must let the user select two `.docx` files — **Original** (left) and **Edited** (right) — via file pickers and drag-and-drop.
2. The system must show each file's name above its panel.
3. The system must provide a "Swap" action that exchanges Original and Edited and re-runs the comparison.
4. The system must reject non-`.docx` files and corrupted/unreadable `.docx` files with a clear error message, without crashing.
5. The system must process files locally only; it must not send document content over the network.
6. The system must show a loading/progress indicator while the comparison engine is downloading and while a comparison runs. Until the app and its engine are ready, a "Loading…" modal with a spinner covers the page; it appears with the first HTML, before the app's scripts have loaded. The UI must stay responsive during comparison, rendering and export: all engine work must run in a Web Worker (see §7.4).

### 4.2 Comparison

7. The system must compare the two documents at **word level** (a changed word is highlighted as a whole word, not individual characters).
8. The system must show these change types in the list:
   - **Inserted** — text present only in Edited
   - **Deleted** — text present only in Original
   - **Replaced** — a deletion and an insertion next to each other in the same paragraph (in either order), shown as **one** item (like Draftable's "REPLACED"). The engine reports these as two revisions; the app groups them, and a decision on the item applies to both.
   - **Formatting changed** — same text, different formatting (e.g. bold, font, paragraph or section properties)
   - **Moved** — a paragraph (or block) relocated to another position, shown as one linked item (source and destination)
   - **Paragraph break** — a paragraph break added or removed with no text change (e.g. an empty paragraph removed, two paragraphs joined)
9. Paragraph-mark revisions that sit next to a text change in the same paragraph must be folded into that text change's item and follow its decision. Only paragraph-mark revisions with no such neighbour appear on their own, as **Paragraph break** items. A paragraph-mark revision that carries real text (the engine can report a whole run of deleted paragraphs this way, e.g. the cut-off tail of the sample) is an ordinary Inserted/Deleted item.
10. The system must compare these document parts: **main body**, **footnotes and endnotes**, and **tables** (cell-level differences inside a table, not a whole-table replacement).
11. Headers/footers, images, and comments are not compared (see Non-Goals). The engine must be configured so that they are not reported as changes, and they must be preserved unchanged in the export.
12. Changes to list-numbering labels caused only by edits elsewhere (e.g. item "(3)" becoming "(4)") must not be reported as changes.
13. If an input document already contains tracked changes, the system must compare the *accepted* view of that document (i.e. as if its existing tracked changes were accepted), and must tell the user it did so.

    *Added after the first browser review (2026-10-16):*

    13a. The system must normalize the text of both documents to Unicode NFC before comparing, so that a letter typed as a base letter plus a combining mark (e.g. "a" + U+0304, as some macOS input methods produce) matches the same precomposed letter ("ā").
    13b. A change whose text is identical in both versions (e.g. a word set in several runs with different fonts in one version and as one run in the other, which the engine reports as a deletion plus an insertion) must be shown as a **Formatting** change, not as Replaced. Likewise a typed list number ("1. ") replaced by automatic list numbering with the same label: the engine reports the typed number's deletion and a paragraph-properties change adding the numbering; together they are one Formatting change (15 on the sample).
    13c. The system must provide a **Compare settings** dialog, opened from the toolbar, with these options, all **on** by default: ignore **quote style** changes (straight, curly, low „ and upper ” quotes; single and double quotes stay distinct; also three dots `...` vs the ellipsis character `…`); ignore **dash** changes (hyphen, en dash, em dash, minus); ignore **whitespace** changes (spaces, tabs, line breaks, paragraph breaks and empty paragraphs). A change is ignored when the text of its paragraph(s) before and after that change is equal under the enabled options. A change that joins or splits words is never ignored. Within a change that is not ignored, the words both sides share at its start or end under the enabled options are shown as plain text: the engine compares whole words, so a quote attached to an unchanged word comes along with the change next to it (e.g. `szövegek "az` → `szutták szövegei “az` highlights only `szövegek` → `szutták szövegei`; 34 replacements on the sample have such edges).
    13d. Ignored changes are shown as plain text in both panels, are not listed or counted among the changes (the number ignored is shown), are not part of navigation or bulk actions, and are exported as in the Edited document, unless the reviewer explicitly accepted or rejected the change before a setting made it ignored: an explicit decision wins over the ignore setting (it is kept, and applies again on export). Changing the settings must not re-run the comparison. The settings are remembered in the browser.

### 4.3 Partially edited documents (comparison range)

14. After comparison, the system must detect a **trailing unedited region**: when the last paragraph of the Original body is wholly deleted (the Edited document has nothing of it), the deletion covering it marks the region, and its first wholly deleted paragraph is the proposed end point. A deletion that only removes some words from the last paragraph is an ordinary change. Small changes after it (e.g. a paragraph break inserted at the very end) do not prevent the detection.
15. When such a region is detected, the system must tell the user (e.g. "The edited document appears to end at paragraph 76 of the original. The remaining N paragraphs are treated as unedited.").
16. The system must let the user set the end point manually: "Compare the Original only up to paragraph N" (choose a paragraph by number or by clicking a paragraph in the left panel). The user must also be able to turn the range off (compare the full documents).
17. Every change located after the end point — in the body and in footnotes/endnotes referenced from there — is **outside the range**: it must not appear in the changes list, it must not count in the totals, and it is always **rejected** on export. Rejecting it keeps the Original's text, so the unedited remainder appears in the exported document **unchanged**.
18. In the left panel, content after the end point must be visually marked as "outside the comparison" (e.g. greyed out, with a divider line), not highlighted as deleted.
19. Changing the end point must not require re-running the comparison; it only reclassifies existing changes.

### 4.4 Side-by-side view

20. The system must render both documents in two panels as **continuous scrolling text** (no page boxes), keeping the documents' readable formatting: headings, paragraph styles, bold/italic, lists, tables, footnotes (shown at the end of the document).
21. The left panel must highlight deleted text (red background, strikethrough) and the right panel must highlight inserted text (blue background, underline), matching the colour conventions of the reference screenshot. Moves must have their own distinct highlight style, and the colours must be explained in a small legend. Changes are marked within the text only, with no rules at the paragraph edge. Formatting changes have no mark in the panels (in a restyled document nearly every line has one, and underlines or rules hurt readability); they are reviewed through the changes list.
22. The two panels must scroll **in sync**: scrolling one panel keeps the matching paragraph aligned in the other.
23. The system must provide a toggle to turn scroll sync off ("Scroll lock", as in Draftable).
24. Each panel must have a narrow overview bar along its edge showing where the changes are in the whole document (like Draftable's change minimap). Clicking a position on the bar scrolls there.
25. Changes the user has already accepted or rejected must be visually distinguishable from undecided ones in both panels (e.g. a dimmed highlight with a ✓ / ✗ marker).

### 4.5 Changes list

26. The system must show a list of all changes in document order. Each item shows: sequence number, change type (Inserted / Deleted / Replaced / Formatting / Moved / Paragraph break), the removed text and/or added text (truncated if long), the location (body / footnote N / table), and the word count change (e.g. "−1 +1"). Formatting items show a readable description of what changed (e.g. "Bold removed, Font changed").
27. Each item must have **Accept** and **Reject** buttons and show the current decision (undecided / accepted / rejected). The user must be able to change a decision or reset it to undecided.
28. Clicking an item must scroll **both** panels to that change and highlight it as the current change.
29. Clicking a highlighted change in either panel must select the corresponding item in the list.
30. **Formatting group:** formatting changes must be collected into one collapsible group, **collapsed by default**, whose header shows the number of formatting changes and their decision counts. The group header must provide **Accept all formatting** and **Reject all formatting**. Expanding the group shows the individual formatting items, each of which can still be decided individually.
31. When the formatting group is collapsed, Previous/Next navigation (FR-33) skips formatting items. When it is expanded, navigation includes them.
32. The system must provide **Accept all** and **Reject all** actions. Since these affect many changes, they must ask for confirmation first and must apply only to changes that are still undecided.
33. The system must provide **Previous change** and **Next change** buttons.
34. The system must provide keyboard shortcuts at minimum for: next change, previous change, accept current change, reject current change. When a change is accepted or rejected via shortcut, the selection moves to the next undecided change. Shortcuts must be listed in a help popover.
35. The list footer must show totals: number of changes, number accepted, rejected and undecided (text changes and formatting changes counted separately).
36. The list must stay responsive with thousands of items (virtualized rendering).

### 4.6 Export

37. The system must provide a **Download** action that produces a new `.docx`.
38. Before downloading, the system must ask how to treat undecided changes, with these options:
    - **Accept** undecided changes (default)
    - **Reject** undecided changes
    The dialog must show how many changes are undecided. Changes outside the comparison range are not affected by this choice (always rejected, FR-17).
39. The exported document must be a **clean** document: it contains no tracked-change markup. Accepted changes take the Edited version, rejected changes keep the Original version.
40. Moved content must be exported correctly: accepting a move places the block at its new position only; rejecting it keeps it at its original position only.
41. The exported document must keep the Original's styles, numbering, footnotes and other document parts, except where accepted changes alter them.
42. The exported file must open in **LibreOffice Writer** without errors or repair prompts, and must pass Docxodus' package verification (`verifyDeliverable`) with no errors.
43. The default filename must be `<edited-file-name>.reviewed.docx`.
44. Export of a ~300-page document must complete in under 10 seconds.
45. Correctness checks:
    - Accepting all changes must produce a document whose text is identical to the Edited document (within the comparison range, plus the unchanged tail from FR-17).
    - Rejecting all changes must produce a document whose text is identical to the Original document.
    - A mixed set of decisions must produce text where each accepted change shows the Edited version and each rejected change shows the Original version.

### 4.7 Saving the review

46. The system must automatically save the review state in the browser (IndexedDB): both input files, the comparison range, and every decision. Saving happens after each change of decision.
47. When the page is reopened, the system must offer to resume the last review ("Resume review of A → B?") or to start a new one.
48. The system must let the user discard the saved review.
49. The saved decisions must be tied to the exact input files (by a content hash) and the engine version. If the files differ from the saved ones, the saved decisions must not be applied.
50. If browser storage is unavailable (e.g. private window, storage full), the tool must keep working without saving and tell the user that the review will not be remembered.

### 4.8 Deployment

51. The app must build to static files and be deployable to GitHub Pages under a project subpath (e.g. `https://<user>.github.io/<repo>/`).
52. The comparison engine's assets must be loaded from the same site (no third-party CDN at runtime), so that the tool works the same regardless of external services.
53. After the first visit, the engine assets must be served from a local cache (service worker), so that repeat visits start quickly and work offline. GitHub Pages only allows browsers to cache files for 10 minutes on their own (`cache-control: max-age=600`).

## 5. Non-Goals (Out of Scope)

- Comparing **headers and footers**, **images**, and **comments** (they are preserved in the export but not diffed).
- **Paginated** (page-by-page, print-layout) rendering. The first version uses continuous text; pages may come later.
- **Character-level** diff granularity.
- **Search** within the documents.
- **Filtering** the changes list by type. The formatting group (FR-30) is the only grouping.
- An option to ignore formatting changes entirely.
- Exporting a `.docx` that still contains Word **tracked changes** (undecided changes are always resolved per the user's choice at export).
- Editing document text inside the tool.
- Exporting/importing the review as a file, sharing reviews between users, or multi-user collaboration.
- Comparing more than two documents, or formats other than `.docx` (PDF, `.doc`, `.odt`).
- Any server, account system, or upload of documents.
- Testing in Microsoft Word (not available on the development machine; LibreOffice and `verifyDeliverable` are the acceptance checks).
- Printing.

## 6. Design Considerations

- **Layout** (based on the Draftable screenshot):
  - **Top toolbar:** file names / load buttons, Swap, Scroll lock toggle, Previous / Next change, comparison range control, Download, Help.
  - **Main area:** Original panel (left) | Edited panel (right), each with its own overview bar of change markers.
  - **Right sidebar:** changes list with Accept/Reject per item, Accept all / Reject all at the top, the collapsible formatting group, totals at the bottom.
- **Colours:** deletions red (left), insertions blue (right), as in the reference screenshot. Moves and formatting changes use two further distinct colours (e.g. purple for moves, amber dotted underline for formatting). Colours must have enough contrast for reading and must not be the only signal (also use strikethrough for deletions, underline for insertions).
- **Formatting changes** are not marked in the panels (decided in milestone 3 review: underlines and paragraph rules hurt readability, since in a restyled document nearly every paragraph has one); the changes list and the current-change outline show them.
- **Empty state:** before files are loaded, show two drop zones with short instructions and a note that files stay on the user's computer.
- **Long documents:** rendering ~300 pages (~2 MB of HTML per panel) must not freeze the page; render the panels incrementally or virtualize them if needed.
- The sidebar should be resizable or collapsible on narrow screens; the primary target is a desktop browser.

## 7. Technical Considerations

### 7.1 Recommended stack

| Concern | Choice | Notes |
|---|---|---|
| Comparison engine, revision list, HTML rendering, final accept pass | **Docxodus** npm package (`docxodus`, MIT, v13.0.0, pinned) — a .NET OOXML engine compiled to WebAssembly | Structure-aware diff producing native Word revisions (`w:ins`/`w:del`/`w:moveFrom`/`w:moveTo`/`w:rPrChange`/`w:pPrChange`); move detection; table and footnote/endnote diffs. Round-trip contract `accept(compare(L,R)) ≡ R`, `reject(compare(L,R)) ≡ L` — **verified on the sample pair** (0 differing lines both ways). |
| Applying individual decisions | **Our own TypeScript code** that rewrites the compared document's XML (see §7.3) | Docxodus' per-revision session API is too slow (see §7.6). |
| Reading/writing the `.docx` zip in TypeScript | `fflate` + `@xmldom/xmldom` | Only `word/document.xml`, `word/footnotes.xml`, `word/endnotes.xml` are rewritten. `DOMParser` is **not available inside Web Workers**, so the worker uses `@xmldom/xmldom` (the same code then runs in Node tests). The main thread may use the native `DOMParser` for the rendered HTML. |
| UI | **React + TypeScript + Vite** | React chosen for the ecosystem (virtualized lists, e.g. `@tanstack/react-virtual`). |
| Engine thread | Our own **module Web Worker** importing `docxodus/core` | The package's `docxodus/worker` proxy does not expose revision listing (see §7.4). |
| Persistence | IndexedDB (e.g. via `idb-keyval`) | Store input file bytes, file hashes, engine version, range, decisions. |
| Offline cache | Service worker (e.g. `vite-plugin-pwa` / Workbox) | Pre-caches the ~40 engine files (FR-53). |
| Hashing | Web Crypto `crypto.subtle.digest('SHA-256')` | Ties saved decisions to the exact input files. |
| Tests | Vitest (unit, and engine tests in **Node** — the Docxodus WASM runs under Node), Playwright (end-to-end in a real browser) | Tests use the two sample documents in `docs/` (committed; tests that need them skip when absent), synthetic fixtures committed in the repo, and a synthetic ~300-page pair. Round-trip text checks via `pandoc -t plain`. |
| Deployment | GitHub Actions → GitHub Pages | Vite `base` set to the repo subpath; copy `node_modules/docxodus/dist/wasm/` into the build output. |

### 7.2 Core data flow

1. **Compare** (in the worker): `docxDiffCompare(original, edited, settings)` → **redline `.docx`** containing tracked changes. Required settings:
   ```ts
   {
     preAcceptInputRevisions: true,   // FR-13: compare the accepted view of each input
     compareHeadersFooters: false,    // FR-11: engine default is true
     trackNumberingChanges: false,    // FR-12: removes numbering-label-only entries
     detectMoves: true,               // default; listed for clarity
   }
   ```
   Do **not** use `compareDocuments`: it only exposes `authorName`/`caseInsensitive` and always compares headers/footers.
2. **List revisions**: `getRevisions(redline)` → `RevisionListEntry[]` (`id`, `type`, `family`, `constituentIds`, `constituentKeys`, `text`, `scope`, `anchorId`, `affectedAnchors`, `resolutionStatus`).
3. **Build change items** (TypeScript). Formatting revisions (`type: "format"`) are interleaved with content revisions in the engine's list, so walk the **non-formatting** revisions in order for these rules:
   - fold a `paragraph_mark` revision whose text is only `¶` characters into the neighbouring (previous or next) revision that shares one of its `affectedAnchors` (any non-formatting revision that is not itself a bare paragraph mark, moves included); otherwise it becomes a **Paragraph break** item (FR-9). On the sample, 43 of the 49 paragraph marks are bare and **26** of them fold (2 of these into a move; restricted to content insert/delete it would be 24 — the "25" measured during planning could not be reproduced), leaving 17 Paragraph break items.
   - a `paragraph_mark` revision with other text is an ordinary Inserted/Deleted item (on the sample, the cut-off tail is one such `delete` with 117,771 characters and 579 anchors).
   - pair a `content_delete` and a `content_insert` that are neighbours (**either order**) and whose text **touches** in the rendered HTML (no unchanged text other than whitespace between them, same paragraph) into **Replaced** (FR-8). A deletion that covers a wholly deleted last Original paragraph (an unedited tail, §7.5) is never paired, so that an insertion touching its start (e.g. a "reviewed up to here" note) does not hide it from the range detection. On the sample there are 110 delete→insert and 143 insert→delete neighbour pairs sharing an anchor (overlapping: a revision can be in two). Pairing greedily by shared anchor alone (milestone 2) gave 147 Replaced items, some of them wrong: in "[del 2. ]Tilos … [ins „szentelt”][del „szentelt"] vizet … [ins orvos][del orvosnak]" it paired "2. " with „szentelt” and „szentelt" with "orvos". Requiring touching text gives **141** Replaced items, all insertion before deletion.
   - formatting revisions go to the formatting group (FR-30).
   Each item keeps the list of engine revision ids it stands for. On the sample: **629 items** — 378 formatting, 141 replaced, 64 deleted, 27 inserted, 17 paragraph break, 2 moved (milestone 2 measured 623 with the shared-anchor pairing). After rendering, 4 Replaced items whose text is identical are relabelled as formatting (FR-13b) and 15 typed list numbers are combined with their automatic numbering into formatting items, which leaves **614 items**. With the default compare settings **54** text changes are ignored (FR-13c); 10 of them need the quote setting (including the ellipsis, task 4.16). Before the ellipsis was folded it was 53: quote style alone 6, dashes alone 8, whitespace alone 35.
4. **Render**: tag the redline (§7.4), then `convertDocxToHtml(taggedRedline, { renderTrackedChanges: true, renderFootnotesAndEndnotes: true, renderMoveOperations: true, stampAnchors: true })` once. Both panels display this same HTML: the left panel hides `<ins>` and move-to content via CSS, the right panel hides `<del>` and move-from content.
5. **Index the document** from the rendered HTML (main thread, `DOMParser`): block order from `data-anchor` (these match the revisions' `affectedAnchors[].unid` — 1,412 of 1,413 on the sample, the miss being a section anchor), and footnote references from `a.footnote-ref[data-footnote-id]`. The redline XML carries **no** anchor ids (the engine computes them), so the range logic (§7.5) works on this index, not on the XML. Classify items as inside/outside the range.
6. **Decisions** are kept in app state and IndexedDB as `itemId → accepted | rejected | undecided`. Comparison output is deterministic (byte-identical redline, identical revision ids for the same inputs and engine version — verified), so item ids are stable across sessions.
7. **Export** (§7.3).

### 7.3 Export algorithm

Docxodus' stateless `docxDiffAcceptRevisions` resolves a whole document correctly and quickly (0.6 s for the sample, 1.1 s for ~300 pages), including the hard cases (paragraph-mark merges, moves). The export therefore turns every "reject" into markup that *accepting* will resolve to the Original version, then accepts everything in one pass:

1. Determine the final decision of every engine revision: for out-of-range revisions **reject**; otherwise the item's explicit decision; otherwise, for items the compare settings ignore, **accept**; otherwise (undecided) the export-dialog choice.
2. Unzip the redline; parse `document.xml`, `footnotes.xml`, `endnotes.xml`.
3. For each revision to **reject**, locate its markup by `constituentKeys` (element QName + `w:id`) and rewrite it:
   - `w:ins` (run content) → rename to `w:del`, convert `w:t` → `w:delText`
   - `w:del` (run content) → unwrap (keep the runs), convert `w:delText` → `w:t`
   - `w:rPrChange` → replace the parent `w:rPr` contents with the stored old `w:rPr`, drop the change
   - `w:pPrChange` → same for paragraph properties, keeping the paragraph's own `w:rPr` and `w:sectPr` and **putting the restored properties first** (schema order: properties, then `w:rPr`, then `w:sectPr`). Getting this order wrong still gives the right text but fails schema validation.
   - `w:sectPrChange` → replace the `w:sectPr` properties with the stored old ones, keeping `w:headerReference`/`w:footerReference` first
   - paragraph mark `w:ins` inside `w:pPr/w:rPr` → rename to `w:del`; paragraph mark `w:del` → remove the marker
   - `w:moveFrom` → unwrap (content stays at the source); `w:moveTo` → treat as `w:del`; remove the matching `w:moveFromRangeStart/End` / `w:moveToRangeStart/End` markers
   - table row/cell insert/delete markers (`w:trPr/w:ins`, `w:trPr/w:del`, `w:cellIns`, `w:cellDel`) → inverse as above
   - table property changes (`w:tblPrChange`, `w:trPrChange`, `w:tcPrChange`, `w:tblGridChange`, `w:tblPrExChange`) → replace the parent properties with the stored old ones, drop the change. `docxDiffCompare` emits these (`refs/Docxodus/Docxodus/DocxDiff.cs`, `Ir/Diff/`), and the engine's revision API treats them like `w:rPrChange` (`Internal/RevisionOps.cs`).
   - The rule for `w:ins`/`w:del` depends on where the element sits (run content, `w:pPr/w:rPr` paragraph mark, `w:trPr` row), not on the key's `kind=`.
4. Re-zip, then call `docxDiffAcceptRevisions(bytes)` once. The result is the clean export.
5. Verify: `listRevisions` / `getRevisions` on the result returns 0 entries.

**Prototype result (PRD review):** a Python/lxml prototype of these rules (`tasks/reference/reject-all-prototype.py`) applied to *every* revision of the sample redline, followed by `docxDiffAcceptRevisions`, produced text identical to the Original (0 differing lines), 0 remaining revisions, `verifyDeliverable` → `passed`, and LibreOffice converted it without error; the accept pass took 0.6 s. Mixed decisions and tables are not yet tested.

**Implementation result (task 3, 2026-10-16):** `src/engine/rejectRewrite.ts` implements the rules above. Tested on 15 synthetic fixture pairs (`test/fixtures/`: insert, delete, replace, run and paragraph formatting, section properties, move, paragraph split and join, table cell edit, table rows, restyled table, footnotes, endnotes, trailing deletion) and on the sample pair:
- all-accept ≡ Edited text and all-reject ≡ Original text everywhere; every export passes `verifyDeliverable` and converts in LibreOffice (`scripts/check-libreoffice.sh`);
- on the fixtures, rejecting any single revision and accepting the rest (and the reverse) gives the same text and the same XML (up to empty property containers) as the engine's own `DocxSession.rejectRevision`/`acceptRevision` followed by the stateless pass;
- on the sample, alternating decisions per item give exactly the text an independent model of the redline predicts (`test/expectedText.ts`).
- Tables: the engine reports an inserted/deleted row as one `row_insert`/`row_delete` revision whose keys cover the row marker (`kind=RowMark`, `w:trPr/w:ins|del`) and every run and paragraph mark in the row, so no extra rule for the row's content is needed. A restyled table gives `w:tblPrChange`, `w:tblGridChange`, `w:trPrChange` (whose old `w:trPr` can be empty) and `w:tcPrChange` (one revision per changed cell set). `w:cellIns`/`w:cellDel`/`w:tblPrExChange` did not occur; their rules are unit-tested only.
- **Notes:** decisions can separate a note's reference from its content. The engine reports a reference that moved to another paragraph as a deletion plus an insertion of the same note id, so rejecting one and accepting the other leaves the note referenced twice, which fails `verifyDeliverable` (the engine's session API gives the same result); accepting the deletion of a note's whole text while its reference stays leaves a note without a paragraph (schema error); and a note whose reference is deleted while its own deletion is rejected stays as an orphan (the session API removes it). After the accept pass, `reconcileNotes` (`src/engine/notes.ts`) gives each extra reference its own copy of the note, gives an empty note an empty paragraph, and removes notes that the redline referenced but the export no longer does.

Revision markup is found through `constituentKeys`, whose formats are: `kind=Content:<ns>:ins:<id>`, `kind=Content:<ns>:del:<id>`, `kind=PropsChange:<ns>:rPrChange:<id>` (likewise `pPrChange`, `sectPrChange`), `kind=ParaMark:<ns>:ins|del:<id>`, for moves `kind=Content:<ns>:moveFrom:<id>:name=<move name>` (likewise `moveTo`), and the range markers without `kind=`: `<ns>:moveFromRangeStart:<id>:name=<move name>`, `<ns>:moveFromRangeEnd:<id>` (likewise `moveTo…`). A `content_delete` revision can also list the `ParaMark` key of the paragraph mark it removes. Parsed by `parseConstituentKey` in `src/engine/ooxml.ts`. `(element name, w:id)` is unique within a part on the sample, but nothing guarantees it (content, paragraph-mark and table-row `w:ins` share the name): `ElementIndex` finds nothing for a key that names several elements and reports it as ambiguous, and the export fails on it like on missing markup.

Any revision whose `resolutionStatus` is not `supported`, or whose markup cannot be located, must make the export fail with a clear message naming the change, rather than produce a silently wrong document.

The rewrite must be covered by tests in Node: all-accept ≡ Edited text, all-reject ≡ Original text, and mixed decisions on the sample pair and on synthetic documents covering each markup kind above (including tables and moves).

### 7.4 Engine worker and linking HTML to revisions

- **Worker:** the package's `docxodus/worker` proxy (`WorkerDocxSession`) has no `listRevisions`, `acceptRevision`, `rejectRevision` or `save`. Write our own module worker that imports `docxodus/core`, calls `initialize(basePath)` with the GitHub Pages subpath, and exposes exactly the operations in §7.2 (compare, list, tag+render, export). Use `prepare()`/warm-up after load so the first comparison isn't slowed. Progress events carry the id of their request and go to that request's listener only (a superseded compare still running in the worker does not move the new one's progress). A worker that fails after loading (e.g. out of memory) puts the app back into the engine error state with Retry.
- **Revision ids in HTML:** the HTML converter emits **no revision id** on `<ins>`/`<del>` (only `data-author`, `data-date`, and `data-move-id` for moves); in the sample, 195 delete revisions render as 4,333 `<del>` elements, so matching by order is not viable. Workaround: before rendering, rewrite the `w:author` attribute of each revision's markup elements to its engine revision id (e.g. `rev:<id>`). The HTML then carries it as `data-author`. The redline used for **export** is the untagged one.
- **Verified on the sample:** every content insert/delete, paragraph-mark and move revision appears in the HTML with its id; **355 of 378** formatting revisions do. The remaining 23 have no visible element of their own (e.g. formatting of an empty run or of section properties). For those, highlight the paragraph(s) named in `affectedAnchors` instead.
- The converter can emit per-author CSS rules (`[data-author="…"]`); none were emitted with the options above, but strip any that appear, since every revision now has its own "author".
- Formatting spans carry a human-readable `title` (e.g. "Bold removed, Font size changed, Font changed"); use it for the formatting item's description (FR-26).
- **Joined and split paragraphs:** the HTML shows the redline's paragraphs as they are, so a paragraph whose mark is deleted still ends where it did. In Word, accepting merges it into the next paragraph, which keeps its own properties. On the sample, typed "1. " numbers were replaced by automatic numbering: the engine kept each paragraph's text, deleted its paragraph mark and inserted an empty numbered paragraph after it, so the Edited panel showed the text before its number. Each panel therefore moves the content of a paragraph whose mark its version lacks (right: deleted, left: inserted) to the start of the next paragraph it shows, after the list label.
- **Scroll sync:** both panels render the same HTML, so every block has the same `data-anchor` in both panels. Sync by finding the top-most visible anchor in the scrolled panel and aligning the same anchor in the other.

### 7.5 Comparison range implementation (FR-14 – FR-19)

- No document trimming and no second comparison. Compare the full documents once, then classify revisions.
- All positions come from the document index built from the rendered HTML (§7.2 step 5). "Original body paragraphs" are the body blocks that are visible in the left panel (i.e. not wholly inside `<ins>`/move-to content).
- **Detection:** only when the **last Original body paragraph** is wholly deleted (not in the Edited document; a word deleted from it is an ordinary change), find the body Deleted item (`content_delete`, or a `paragraph_mark` delete carrying text) whose anchors include it. Its first **wholly deleted** Original paragraph is the proposed end point. When the deletion starts within a paragraph the Edited document keeps part of, that paragraph stays in range; the deletion spans the end point and is out of range as a whole (rejected, so the paragraph keeps its Original text plus any in-range edits). Do **not** require it to be the last revision: on the sample it is followed by two small paragraph-mark inserts and a formatting change. Verified on the sample: the whole unedited tail is **one** revision (`paragraph_mark` delete, 117,771 characters, 579 anchors).
- **Footnotes/endnotes** in the range: from the index, map each `data-footnote-id` reference (endnotes: `a.endnote-ref`, `href="#en-<id>"`) to the body paragraph containing it; a note referenced more than once maps to its first reference. A note revision is outside the range when its note is referenced only from paragraphs after the end point. (In the sample, **15** footnote deletions — notes 6–20 — belong to the tail. The sample has 18 footnote deletion revisions in all; the other 3 are note 5, deleted in the edited part, and one each in the Replaced items of notes 2 and 4.)
- **Measured on the sample:** the rendered HTML has 775 anchored blocks, 747 of them Original body paragraphs (blocks not wholly inside `<ins>`/move-to content; list labels don't count as text; an empty block counts unless its paragraph mark is inserted). Milestone 2 counted 733: it took the inserted list label of the 14 empty Original paragraphs between list items (which received automatic numbering) for inserted text. The proposed end point is paragraph index **168** (0-based; milestone 2: 154); the tail covers the remaining 579. Out of range with it: the tail deletion, the 15 tail footnote deletions, the 2 moves (see §7.8 item 5 — this loses the editor's changes to the last two in-range paragraphs and misplaces them; task 6.8), and the 2 items the engine placed after the deleted tail — a bare paragraph-mark insertion and the Edited document's closing marker paragraph "(Átnézve eddig, Stillness Flowing p.257)". Rejecting the latter on export drops that marker, which is what a reviewer wants for a "reviewed up to here" note.
- **Positions:** a block that is not in the Original (inserted paragraph) sits half a step after the Original paragraph before it, so an insertion right after the last in-range paragraph stays in range, while content the engine placed after a deleted tail falls outside.
- **Manual end point:** a paragraph's position is its index among the Original body paragraphs. Revisions anchored after the end point are outside the range. If one deletion revision spans the end point, the whole revision is treated as outside the range; tell the user.
- Out-of-range revisions are always rejected on export (FR-17), which keeps the Original's text.

### 7.6 Measured performance and constraints

With the final settings (§7.2) the sample pair gives **796** revisions: 378 formatting, 200 content delete, 167 content insert, 49 paragraph mark, 2 moves. The table below was measured before `trackNumberingChanges: false` was added (822 revisions); timings are unaffected in practice.

| Engine init | 0.15 s (files local) | — |

| `docxDiffAcceptRevisions` (stateless) | 0.6 s | 1.1 s |

| Session per-revision accept/reject, 822 calls | **86 s**, 16 `revision_not_found` failures | — |
| Peak memory (RSS) | — | ~450 MB |

- **Do not use `DocxSession` for applying decisions.** It costs ~100 ms per revision even with `undoDepth: 0`, and resolving one revision can consume linked ones (paragraph marks, move halves), invalidating ids still to be processed.
- **Download size:** the engine is ~21 MB uncompressed. GitHub Pages compresses `.wasm` with gzip (verified against the Docxodus demo on GitHub Pages: `dotnet.native.wasm` 3.2 MB gzipped); expect ~6.5 MB total on first load. GitHub Pages ignores the shipped `.br` files. Start loading the engine as soon as the page opens and show progress.

Under Node, `initialize` takes 0.14 s and the warm-up (`DocumentComparer.Warmup()`) 0.44 s.

In total **6.4 s in the module worker in headless Chromium** and ~7 s under Node. Main-thread analysis (index + items + range): 0.53 s under jsdom, of which `buildChangeItems` takes 7 ms.

Longest main-thread tasks 180–190 ms (inserting the ~1.2 MB HTML into both panels and the first layout); the page keeps responding while the worker compares. Synthetic ~300-page pair: panels shown after **12.8 s** (worker 12.0 s, main-thread preparation 56 ms), longest main-thread task 271 ms, no long tasks while scrolling, so the HTML is inserted in one go (no chunking). Accept-all export (`docxDiffAcceptRevisions` + revision check): 0.65 s for the ~300-page pair.
- **Export, task 3 (2026-10-16), Node:** sample pair: all accepted 0.6 s, all rejected 1.3 s, alternating per item 0.9–1.4 s (reject rewrite + `docxDiffAcceptRevisions` + note reconciliation + the zero-revisions check). Synthetic ~300-page pair (2,411 revisions): all accepted 0.59 s, all rejected 0.78 s, alternating 0.76 s, of which the reject rewrite (unzip, xmldom, zip) 0.05–0.21 s. Well under the 10 s of FR-44.
- **Engine version at run time:** `getVersion()` reports only `"Docxodus WASM"` and the .NET version (10.0.12), not the npm package version. The build injects the package version from `node_modules/docxodus/package.json` as `__DOCXODUS_VERSION__` (`vite.config.ts`); that is the version saved with a review (FR-49).
- **Caching:** GitHub Pages sends `cache-control: max-age=600`, hence the service worker (FR-53).
- **Engine is .NET:** the algorithm cannot easily be changed from our side; bugs must be worked around or reported upstream. Reference sources are in `refs/Docxodus` (`docs/architecture/ir_diff_engine.md` describes the algorithm; `Docxodus/RevisionProcessor.cs` the accept/reject logic).
- **Pin the engine version** exactly; the saved review (FR-49) records it, since revision ids and grouping can change between engine versions.

## 8. Success Metrics

1. With the two sample documents, the tool detects the edited-region end automatically; the changes list then contains only changes within the edited part, with the ~360 formatting changes in the collapsed formatting group.
2. Accept all → export gives text identical to the Edited document (+ unchanged tail); Reject all → export gives text identical to the Original. Verified by automated tests.
3. Exported files open in LibreOffice Writer with no repair prompt and pass `verifyDeliverable`.
4. After the engine has loaded, a ~60-page pair is compared and displayed in under 10 seconds, and a ~300-page pair in under 60 seconds, on a typical laptop. Export takes under 10 seconds. The UI stays responsive (no frozen page) throughout.
5. A review can be closed and resumed with all decisions intact.
6. The app runs from GitHub Pages with no network requests other than loading its own static assets, and repeat visits work offline.

## 9. Open Questions

1. Comparison range: is the end point always at the end of the Original, or could the edited region also start later than the beginning (an edited middle section)? Currently only a trailing unedited region is in scope.
2. Is the first-load download of ~6.5 MB acceptable, or is there a size budget?
3. Exact keyboard shortcut bindings (proposed: `j`/`k` or `↓`/`↑` for next/previous, `a` accept, `r` reject).
4. Should the export also offer a version with the remaining undecided changes kept as tracked changes, for a second reviewer? (Currently a non-goal.)
